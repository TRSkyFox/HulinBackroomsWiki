# 事件与日志结构规范（重要交接文件）

> 这份文件是依照用户逐段说明的游戏实际画面整理的**事件结构正本**。
> 目的：让后续接手的 agent 不需要重新猜事件边界，也不会再把路口、事件、楼层介绍混在一起。
>
> 目前状态：Wiki 内所有旧事件记录已先全部移除（`EVB_NODES = {}`、动态事件节点停用、楼层 `_events`/`AUTO-EVENTS` 已清空）。
> **在依本文件重做 parser 并通过范例验证之前，不要把事件资料重新写回正式 Wiki。**

---

## 0. 一句话总结

```text
楼层 transition
  → 楼层标题／楼层介绍
  → 玩家角色台词
  → 路口（路口文本＋路径选项）
  → 事件（事件名＋事件介绍＋行动选项）
  → 判定／结果／效果
  → 看完按“继续”
  → 出口进度 +1
  → 下一个路口
```

楼层出口事件是另一个独立事件；完成本层所需事件后，通常会强制进入出口事件。

## 1. 楼层相关

### 1.1 切层黑屏

切换楼层时，画面固定全黑，中央显示楼层名。

正常第一次到未知楼层：

```text
Level ???
(???)
```

已知道楼层名时（例如被动／后室百科／已探索）：

```text
Level 0.41
(病)
```

特殊楼层：

```text
The Void“虚空”
```

分类：

```text
floor.transition.title
floor.transition.subtitle
```

这不是楼层介绍，也不是事件正文。

### 1.2 楼层名何时显示

- 正常第一次到某层：显示 `???`
- 走过该层一半进度后：才显示真实楼层名
- 队伍有特殊被动：进入时可直接看到名字
- `后室百科`：进入时直接知道楼层名，切层黑屏就直接显示真实名称

因此楼层名一定要有“已知／未知”与“揭示来源”：

```text
floor.known = true | false
floor.revealSource =
  unknown
  progress
  passive:后室百科
  ability
```

### 1.3 顶部 HUD 楼层名

游戏画面顶部会显示：

```text
Level 0.01“出口?”
第 2 层｜距离：入口附近｜岔路
```

或：

```text
Level 161“阿帕拉契的荒凉”
第 2 层｜1980 年 1 月｜区域：树林｜岔路
```

分类：

```text
floor.title
floor.meta
```

注意：

- `第 N 層` 是**本局楼层计数**，不是 `Level N`。
- `floor.title` 和正文中的 `floor.header` 可能不一致。
- 例如顶部已显示 `Level 161「阿帕拉契的荒涼」`，正文仍可能是 `—— Level ???「???」 ——`。
- 这两个字段要分开记录，不能互相覆盖。

### 1.4 正文楼层标题

正文中的黄色标题线：

```text
—— Level 161“阿帕拉契的荒凉” ——
```

未知时：

```text
—— Level ???“???” ——
```

分类：

```text
floor.header
```

### 1.5 角色开场文本

本局刚开始、角色第一次进入游戏时，红框区域会有一段角色开场文字。

例：

```text
切出现实
前一秒，你还站在原地的地方——天狐盯着一面泛黄的墙纸研究了很久，想弄懂它为什么会这么黄——再抬起头的时候，四周全是一样的墙纸。
下一秒，脚下的地板好像突然消失了，整个人往旁边一滑。
回过神来，你已经摔在一片湿湿的地毯上。四周是发霉的黄色壁纸，头顶的日光灯嗡嗡嗡地响个不停。
四周一个人也没有。天狐小声地问了一句，也不知道是在问谁：“……这里是哪里？”
```

规则：

- 只在本局开始时出现
- 通常不会往上翻特意去看
- **不是楼层介绍**
- 不进 `floor.intro`

分类：

```text
character.intro
```

### 1.6 楼层介绍

黄框区域是当前楼层名＋楼层介绍。

例：

```text
—— Level 0“大厅” ——
单调的黄色壁纸、潮湿的地毯、到处都是的电源插座，还有头顶那永远不会停的日光灯嗡嗡声，比一般的日光灯吵得多，吵到太阳穴一跳一跳地痛。
这里的每一个房间都长得差不多，却没有两个完全一样。你试著走直线，回头时却发现身后已经换成了另一组房间。
一个人也没有，除了嗡嗡声，什么都听不到。待久了，连自己的脑袋都开始不太可靠。
```

规则：

- `floor.intro` 只收楼层／环境介绍
- **不要记录玩家角色说的话**
- 角色台词、能力揭示、系统结算都不能混进 `floor.intro`

### 1.7 玩家角色台词

绿色／金色文字：

```text
天狐：“好热，灯又闪得好凶。我的眼睛在申请下班。”
```

结构：

```text
玩家名：该玩家选择的角色说的话
```

分类：

```text
dialogue.player
```

字段：

```text
speakerRaw     画面上的玩家名，例如“天狐”
text           引号内的角色台词
```

Wiki 正式内容要依 `AGENTS.md` 的玩家名／角色名规则处理；原始 log 保留 `speakerRaw`，不要直接删。

### 1.8 能力／图鉴揭示

紫色文字，例如：

```text
天狐在心里翻到这一页：Level 0.01“出口?”。
```

或：

```text
天狐一眼就认出来了：这里是 Level 161“阿帕拉契的荒凉”。
```

分类：

```text
ability.reveal
```

规则：

- 这不是通用楼层介绍
- 只有部分角色／能力会有
- `后室百科` 通常直接在切层黑屏与正文标题显示真名，**不会**再出现紫色揭示句
- 不能把紫色句当成所有楼层的固定字段

### 1.9 后室百科与一般被动的差异

用户实例：

| 情况 | 切层黑屏 | 正文标题 | 紫色揭示句 |
|---|---|---|---|
| 一般角色、未知楼层 | `Level ???` `(???)` | `—— Level ???「???」 ——` | 可能有 |
| 带后室百科 | `Level 0.41` `(病)` | `—— Level 0.41「病」 ——` | 没有 |
| 其他洞察能力 | 可能仍 `???` | 可能仍 `???` | 可能有 |

所以 parser 不能假设“紫色句一定存在”，也不能假设“顶部有真名，正文就一定有真名”。

## 2. 路口（Junction）

### 2.1 定义

路口是“选择要往哪里走”的地方。

固定提示：

```text
要走哪条路？
```

事件内部的行动提示则是：

```text
要怎么做？
```

两者不可混。

### 2.2 路口文本

路口提示前面的最后一段白字，是路口文本。

例：

```text
一直往下掉。也可能是往上。这里没有方向。
```

例：

```text
没有声音。连自己的呼吸声，都好像被什么吸走了。
```

例：

```text
树林安静得不自然——没有鸟，没有虫。
```

分类：

```text
junction.text
```

**这不是 `event.story`。**

### 2.3 路口前可能先有角色台词

顺序可能是：

```text
junction.text
dialogue.player
junction.prompt
```

例：

```text
没有声音。连自己的呼吸声，都好像被什么吸走了。
天狐：“好黑……论坛上说黑的地方要特别小心。”
要走哪条路？
```

角色台词仍记 `dialogue.player`，不是路口文本。

### 2.4 路口路径

例：

```text
要走哪条路？
- 伸手往黑暗里抓
- 往更深的地方沉
- 让身体自己转
  （只有你察觉到）你隐约听见那边有声音——不是脚步声，比较像是有什么东西在运转。
  [说出来]
```

分类：

```text
junction.prompt
junction.paths[]
```

每个 path：

```text
path.text
path.perception = true | false
path.hint
path.hintKind
path.announce
```

### 2.5 感知提示（可出现在任何路径）

感知不是一种独立的路径类型。

任何一条 `junction.path` 都可能在玩家感知足够时，额外显示一段提示，告诉玩家这条路**可能通向什么类型的事件**。

例：

```text
（只有你察觉到）那边好像有什么不寻常的东西在等著。
```

例：

```text
（只有你察觉到）你隐约听见那边有声音——不是脚步声，比较像是有什么东西在运转。
```

例：

```text
跟著火把走
（只有你察觉到）你听见那边有很慢很慢的流水声。
```

规则：

- 感知提示是挂在 path 上的附加字段，不是把 path 改成另一种类型。
- 可能 0 条、1 条、多条 path 同时有提示。
- 这只是**模糊类型提示**
- 不是事件名
- 不是事件正文
- 不可自行补成“机械事件”或某个具体事件
- 可以记粗略 `path.hintKind`，但要标低信心
- 右边“说出来”是分享情报的 UI，不是 path 文本

```text
path.perception = true
path.hint = 原始提示
path.hintKind = 声音 / 机械运转（模糊）
path.announce = true
```

### 2.6 选中路径

选中路径后，日志会出现：

```text
→ 你决定：“伸手往黑暗里抓”
```

分类：

```text
path.selected
```

这一行是“已选路径”，不是事件名，也不是新的路口。

### 2.7 路径数量不固定

可能是：

```text
2 个
3 个
```

不要写死。

### 2.8 多数决 UI

```text
跟随多数：关
```

是 UI，不进 log。

## 3. 事件（Event）

### 3.1 事件开始

选完路径后进入事件。

事件名用 `【】` 包住：

```text
【一个颜色】
```

分类：

```text
event.name = 一个颜色
```

### 3.2 顶部事件列

进入事件后，顶部楼层列会由区域变成事件名：

```text
第 3 层｜一个颜色
```

分类：

```text
event.meta
```

规则：

- 事件名可能和顶部这行重复，只记一次 `event.name`
- 顶部这行有时还会塞难度、楼层特殊机制
- **不要和 `floor.meta`／区域混淆**
- 事件结束后，顶部应回到区域／岔路

### 3.3 事件介绍

```text
什么都看不到。你试著想一个颜色——
黑暗里，好像真的浮出了一点点那个颜色。很淡、很淡。
```

分类：

```text
event.intro
```

### 3.4 事件提示

```text
要怎么做？
```

分类：

```text
event.prompt
```

不是 `要走哪条路？`。

### 3.5 事件行动

例：

```text
- 一直想著它，让它变大
  智力 难度 12
- 看著它消失
```

分类：

```text
event.actions[]
```

每个 action：

```text
action.text
action.check.attribute
action.check.hasCheck
action.check.difficulty = variable（不记实际数字）
```

### 3.6 判定

例：

```text
（智力 难度 12）天狐 掷出 17+6=23 → 成功
```

分类：

```text
action.selected
check.attribute
check.outcome
```

**硬性规则：不要记录具体难度数字，也不要记录骰值。**

原因：不同游戏难度、探索进度、队伍状态下，判定难度差异极大，记固定数字会误导。

只记：

```text
check.attribute = 智力
check.hasCheck = true
check.outcome = success | failure
check.difficulty = variable
check.roll = 不记录
```

### 3.7 结果

成功分支例：

```text
那个颜色慢慢变大，大得像一扇门。你朝它划过去。它没有消失。
```

分类：

```text
result.text
```

成功／失败是不同分支，不可合并成同一个 result。

```text
event.action
  check
    success → result.success
    failure → result.failure
```

### 3.8 效果

例：

```text
天狐：经验 +1
```

分类：

```text
result.effects[]
```

例：

```text
effects = [
  { target: 天狐, kind: 经验, amount: 1 }
]
```

不要只把“经验 +1”塞进 result 文字，效果要独立字段。

### 3.9 事件完成

结果下方：

```text
看完之后按“继续”
[继续] (0/1 人看完了)
```

`继续` 是事件结束确认，不是事件内容，也不是路口。

按下继续后：

```text
event.completed = true
```

**事件不是结果一出现就结束；要按继续才结束。**

## 4. 出口进度与出口事件

事件完成后会出现：

```text
出口进度 1/5
```

分类：

```text
floor.progress.current = 1
floor.progress.total = 5
```

代表：

- 本层已完成 1 个事件
- 本层需要完成 5 个事件

完成所有事件后，会进入**出口事件**，把玩家送到其他楼层。

规则：

- 出口事件通常是**强制**的
- 大部分楼层允许最多额外探索 2 个事件
- `The Void` 不允许额外事件
- 出口事件本身要算独立事件，不要并进最后一个普通事件

```text
floor.exitEvent.started
floor.exitEvent.forced = true
floor.extraEventsAllowed = 2（大部分楼层）
The Void：0
```

## 5. 事件生命周期（状态机）

```text
floor_transition
  ↓
floor_header / floor_intro
  ↓
dialogue.player（可选）
  ↓
junction
  ├─ junction.text
  ├─ dialogue.player（可选）
  ├─ junction.prompt
  └─ junction.paths[]
       ↓ 选中路径
path.selected
  ↓
event
  ├─ event.name
  ├─ event.meta
  ├─ event.intro
  ├─ event.prompt
  └─ event.actions[]
       ↓ 选中行动
action.selected
  ↓
check（可选）
  ↓
result.success / result.failure
  ↓
result.effects[]
  ↓
看完按继续
  ↓
event.completed
  ↓
floor.progress +1
  ↓
下一个 junction
```

若本层事件完成数达到 total：

```text
floor.exitEvent
  ↓
切层黑屏
  ↓
下一层
```

## 6. 文字颜色与画面位置

### 6.1 颜色是辅助，不是唯一依据

不同楼层有自己的配色，同一个颜色在不同楼层可能代表不同东西。

例：

- 红色可能是楼层标题
- 红色也可能是危险提示或受伤
- 黄色可能是楼层标题线、路口提示或选项
- 白色可能是楼层介绍、路口文本或事件正文

**分类必须同时看：颜色＋区域＋前后文。**

### 6.2 目前观察到的常见对应

```text
红色／橙红     楼层标题、区域信息、危险提示、系统结算
橙色           系统结算、转场结算
紫色           能力／图鉴／洞察揭示
黄色           正文楼层标题线、路口提示、选项
绿色／金色     玩家角色台词
白色           楼层介绍、路口文本、事件正文、结果
灰色／浅灰     次要说明、条件、补充
```

### 6.3 以位置与锚点分类

优先使用固定文字锚点：

```text
Level ??? / Level N         → floor.transition 或 floor.title
—— ... ——                   → floor.header
要走哪条路？                → junction.prompt
要怎么做？                  → event.prompt
看完之后按“继续”          → event.completed
出口进度 N/M                → floor.progress
【事件名】                  → event.name
→ 你决定：“...”            → path.selected / action.selected
（... 难度 ...）... → 成功   → check
```

### 6.4 重复文本

同一句角色台词可能同时出现在：

- 正文绿色台词行
- 画面中间／右上角漂浮气泡

只记一条 `dialogue.player`；气泡不另记。

## 7. 日志 JSONL 建议格式

以下只是结构建议，实际档名／字段可调，但**语义必须保留**。

```json
{"ts":"...","type":"floor_transition","floorId":"0.41","name":"病","known":true,"revealSource":"passive:后室百科"}
{"ts":"...","type":"floor_title","floorId":"0.41","title":"Level 0.41“病”","meta":"第 3 层｜区域：腐烂的大厅｜岔路"}
{"ts":"...","type":"floor_header","floorId":"0.41","text":"—— Level 0.41“病” ——"}
{"ts":"...","type":"floor_intro","floorId":"0.41","text":"黄色的大厅，可是不对。……"}
{"ts":"...","type":"dialogue","speaker":"天狐","text":"好、好安静……我听得到自己的心跳。"}
{"ts":"...","type":"junction","floorId":"0.41","text":"一直往下掉。也可能是往上。这里没有方向。","prompt":"要走哪条路？","paths":[{"text":"往更深的地方沉","perception":false},{"text":"伸手往黑暗里抓","perception":true,"hint":"那边好像有什么不寻常的东西在等著","announce":true}]}
{"ts":"...","type":"path_selected","text":"伸手往黑暗里抓"}
{"ts":"...","type":"event","floorId":"0.41","name":"一个颜色","meta":"第 3 层｜一个颜色","intro":"什么都看不到。你试著想一个颜色——…","prompt":"要怎么做？"}
{"ts":"...","type":"action_selected","text":"一直想著它，让它变大"}
{"ts":"...","type":"check","attribute":"智力","hasCheck":true,"outcome":"success","difficulty":"variable","roll":null}
{"ts":"...","type":"result","branch":"success","text":"那个颜色慢慢变大，大得像一扇门。你朝它划过去。它没有消失。"}
{"ts":"...","type":"effect","target":"天狐","kind":"经验","amount":1}
{"ts":"...","type":"event_completed","eventName":"一个颜色"}
{"ts":"...","type":"progress","current":1,"total":5}
```

### 7.1 不要写入的字段

```text
check.difficulty 的实际数字
check.roll 的实际骰值
check.bonus 的实际加值
```

可以保留：

```text
check.hasCheck
check.attribute
check.outcome
check.difficulty = "variable"
```

### 7.2 必须保留的来源

```text
rawText         OCR 原文
source          ocr / manual
confidence      OCR 信心
frame/session   哪一帧、哪一场
```

宁可保留低信心 raw，也不要猜一个错的事件。

## 8. 楼层／事件边界规则

### 8.1 新楼层开始

```text
切层黑屏
→ floor_transition
→ 楼层标题／介绍
```

### 8.2 事件开始

```text
path.selected
→ 【事件名】
→ event.name
```

### 8.3 事件结束

```text
看完之后按“继续”
→ event.completed
```

### 8.4 下一个路口

```text
event.completed
→ 出口进度 N/M
→ junction.text
→ 要走哪条路？
```

### 8.5 不可跨越边界合并

不可把：

```text
上一段 event.result
+ 系统结算
+ 新楼层 floor.intro
```

合并成同一段。

也不可把：

```text
路口文本
+ 事件名
+ 事件介绍
```

合并成同一事件。

## 15. 追加实例：The Void 的五个事件（无判定／成功／失败）

以下四个画面补齐了“事件不一定有判定”与“失败分支”的情况。

### 15.1 出口进度

`出口進度 N/M` 是事件完成后的层内进度，不是路口或事件正文。

```text
event.completed
→ floor.progress.current += 1
```

当看到：

```text
出口进度 5/5
```

代表本层普通事件已完成，接下来会进入**出口事件**（通常强制）。

---

### 15.2 无判定事件：`【背后】`

画面顺序：

```text
出口进度 1/5
junction.text = 没有声音。连自己的呼吸声，都好像被什么吸走了。
dialogue.player = 天狐：“好黑……论坛上说黑的地方要特别小心。”
path.selected = → 你决定：“让身体自己转”

event.name = 背后
event.intro =
背后好像有什么。
不是声音，也不是看到，是一种“有东西在”的感觉。很近，就在伸手碰得到的地方。

action.selected = → 你决定：“猛地回头”
result.text =
回头。什么都没有。黑暗。转回来——也是黑暗。分不清楚刚刚是回头了，还是转了一整圈。
effect = 天狐：理智 -1
出口进度 2/5
```

重点：

- 这个事件没有 check
- `action.selected` 后直接 result
- result 后直接 effect
- 不可因为没有“成功／失败”就漏记整个事件

```text
action.check.hasCheck = false
result.text = ...
result.effects = [{ target:"天狐", kind:"理智", amount:-1 }]
```

---

### 15.3 成功分支：`【飘过去的回忆】`

```text
出口进度 2/5
junction.text = 一直往下掉。也可能是往上。这里没有方向。
path.selected = → 你决定：“往记得的方向掉”

event.name = 飘过去的回忆
event.intro =
黑暗里，有一段回忆从旁边飘过去。
不是看到，是想起来。一个夏天的下午、一张旧沙发、电风扇的声音。好像是你的，又好像不是。

action.selected = → 你决定：“伸手抓住它”
check = （感知 难度 11）天狐 掷出 19+4=23 → 成功
result.text =
你抓住了。是你的——你小时候的家，沙发上有一个被你烧出来的小洞。你都忘了有那个洞。现在想起来了。
effect = 天狐：理智 +1
出口进度 3/5
```

只记：

```text
check.attribute = 感知
check.outcome = success
check.difficulty = variable
check.roll = null
```

不记 `難度 11`、`19+4=23`。

---

### 15.4 失败分支：`【掉了多久】`

```text
出口进度 3/5
dialogue.player = 天狐：“看不到自己的手……好可怕。”
path.selected = → 你决定：“往更深的地方沉”

event.name = 掉了多久
event.intro =
你开始数。一、二、三……
数到一百多的时候，突然不确定自己刚刚数到哪里。说不定已经数了好几千次。说不定一次都没有开始。

action.selected = → 你决定：“从头再数一次，数得慢一点”
check = （智力 难度 12）天狐 掷出 3+6=9 → 失败
result.text =
数到一半，数字自己跑掉了。你数到的最后一个数字是“好久”。
effect = 天狐：理智 -1
出口进度 4/5
```

重点：

- 失败分支和成功分支结构相同
- 只是 `check.outcome = failure`，result 文字不同
- 不要把失败结果丢掉，也不要把失败记成成功

---

### 15.5 无判定＋技能式行动：`【一个名字】`

```text
出口进度 4/5
junction.text = 四周全黑。不是暗，是黑，像闭著眼睛，可是眼睛明明张著。
path.selected = → 你决定：“往更深的地方沉”

event.name = 一个名字
event.intro =
黑暗里，你突然想不起一个人的名字。
是一起走的人。一路上叫过很多次的名字。第一个字还在，后面的……像沙子一样一直漏掉。

action.selected = → 你决定：“记性好的人，把一路上发生的事从头想一遍”
（无 check）
result.text =
天狐 从掉进来的那一刻往回翻：上一层、上上一层、第一个遇到的人、第一次一起吃的东西……每一件都想起来了。名字一个都没有漏掉。
effect = 天狐：理智 +1
dialogue.player = 天狐：“口好渴……杏仁水，还有杏仁水吗？”
status = 口渴 3
出口进度 5/5
```

重点：

- 行动可能没有数值判定，而是靠角色能力／描述直接成功
- 仍记 `action.check.hasCheck = false`
- `（口渴 3）` 是状态，不是台词内容
- 台词与状态分开：

```text
dialogue.player.text = 口好渴……杏仁水，还有杏仁水吗？
status.thirst = 3
```

- `出口進度 5/5` 代表普通事件结束，下一步是出口事件，不是再普通路口

---

### 15.6 `→ 你决定` 的两种意思

同一个前缀有两种角色：

#### 路径选择

```text
→ 你决定：“往更深的地方沉”
【事件名】
```

下一行是 `【事件名】` → `path.selected`。

#### 事件行动选择

```text
→ 你决定：“猛地回头”
（判定／结果）
```

下一行是 check、result 或效果 → `action.selected`。

Parser 必须看**下一行**，不能只看 `→ 你决定`。

---

### 15.7 事件后的台词与状态

事件结果／效果后面仍可能出现玩家台词：

```text
effect
dialogue.player
status
出口进度
```

例：

```text
天狐：理智 +1
天狐：“口好渴……杏仁水，还有杏仁水吗？”（口渴 3）
出口进度 5/5
```

不可把这句台词算进 result，也不可把 `口渴 3` 算进台词文字。

---

### 15.8 五事件结构总表

| 进度 | 事件 | 判定 | 结果 | 效果 |
|---|---|---|---|---|
| 1/5 → 2/5 | 背后 | 无 | 回头什么都没有 | 理智 -1 |
| 2/5 → 3/5 | 飘过去的回忆 | 感知，成功 | 抓住回忆 | 理智 +1 |
| 3/5 → 4/5 | 掉了多久 | 智力，失败 | 数字跑掉 | 理智 -1 |
| 4/5 → 5/5 | 一个名字 | 无／角色能力 | 想起名字 | 理智 +1、口渴 3 |
| 5/5 | 出口事件 | 未说明 | 未说明 | 未说明 |

`【背后】` 与 `【一个名字】` 证明：

```text
事件可以没有掷骰
事件可以不显示成功／失败
但事件仍然有 event.name / event.intro / action / result / effect
```

## 16. 出口事件：`【光】`

出口事件不是普通路口，也不是普通事件；它是完成本层普通事件后**强制**进入的事件。

### 16.1 画面顺序

```text
floor.progress = 5/5

exit.lead =
走了这么久，出口应该就在附近了。

dialogue.player =
天狐：“可以用手机的手电筒吗？……电量只剩一点点。”

exit.signal =
空气变了——这一层走到尽头了。

event.name = 光
event.kind = exit
event.forced = true

event.intro =
下面有光。越来越近、越来越亮——亮到眼睛发痛。
风回来了，声音回来了，往下掉的感觉一下子变得好真实。

event.prompt = 要怎么做？

event.actions = [
  {
    text: 放手，让它带你去,
    forced: true
  }
]

action.selected =
→ 你决定：“放手，让它带你去”

result.text =
光一下子扑了上来。你从天花板上摔了下来，摔在一片真的、硬硬的地上。

system.transition =
(走出了这一层——这段路的记忆留了下来：你的记忆碎片 +3)
已经走过 3 层了——你：经验 +3

floor.header = —— Level 0“大厅”——
floor.intro = 单调的黄色壁纸、潮湿的地毯……
dialogue.player = 天狐：“冷静……文章说，第一步是不要慌。”
```

### 16.2 规则

- `出口進度 5/5` 代表普通事件已完成，接著才是出口事件。
- 出口事件仍然是 `event`，有名称 `【光】`。
- 出口事件通常只有一个强制行动：

```text
event.actions.length = 1
event.actions[0].forced = true
```

- 没有 `要走哪条路？`，也没有普通 `junction.paths`。
- `走了这么久，出口应该就在附近了。` 是出口事件的前导文本，不是楼层介绍。
- `空气变了——这一层走到尽头了。` 是出口讯号，不是事件正文。
- 出口结果之后才是：
  - 系统结算（记忆碎片、经验）
  - 下一层的楼层标题
  - 下一层的楼层介绍
  - 下一层的角色台词

### 16.3 不可混淆

```text
出口事件【光】
≠ 下一层的 floor.intro
≠ 普通路口
≠ 普通事件【…】
```

`【光】` 的结果是“摔到下一层”，不是下一层介绍。

### 16.4 记录字段

```text
exitEvent.started = true
exitEvent.forced = true
exitEvent.name = 光
exitEvent.lead
exitEvent.signal
exitEvent.intro
exitEvent.action
exitEvent.result
exitEvent.completed
```

出口事件完成后，才开始记下一层：

```text
floor.transition
floor.title
floor.header
floor.intro
dialogue.player
```

## 17. 出口事件后的新楼层

图中 `【光】` 之后直接出现：

```text
Level 0“大厅”
单调的黄色壁纸……
天狐：“冷静……文章说，第一步是不要慌。”
```

这些全部属于**下一层**，不是出口事件的结果：

```text
floor.header = Level 0“大厅”
floor.intro = 单调的黄色壁纸……
dialogue.player = 天狐：“冷静……文章说，第一步是不要慌。”
```

因此 parser 必须在 `exitEvent.result` 后切边界：

```text
exitEvent.result
→ system.transition
→ floor.transition / floor.header
→ floor.intro
→ dialogue.player
```

不可把下一层的 `floor.intro` 接到出口事件 `【光】` 的 result 里。

## 18. 出口事件的另一种样貌：可延后离开

第 16 节的 `【光】` 是“只有一个强制行动”的出口事件；这一节补上另一种更常见的出口事件：

```text
【出口的门】
要怎么做？
- 推开绿色的出口门
- 把手伸进那个洞，拉开门
- 先不走，再多探索几步
```

### 18.1 出口事件不是固定只有一个行动

```text
event.kind = exit
event.actions = [
  { text: 推开绿色的出口门, kind: exit },
  { text: 把手伸进那个洞，拉开门, kind: exit_alt },
  { text: 先不走，再多探索几步, kind: explore_more }
]
```

- `exit` / `exit_alt`：真正的出口
- `explore_more`：先不离开，回去探索额外事件
- 这个第三选项是**绝大多数楼层出口事件的常见类型**

所以“出口事件通常强制”要精确写成：

```text
出口事件最终是强制的
但玩家可以用“先不走，再多探索几步”延后
```

`The Void` 没有额外事件，所以它的 `【光】` 只有一个强制行动。

### 18.2 选择“先不走”的结果

```text
action.selected = → 你决定：“先不走，再多探索几步”
result.text =
你决定先不走。出口就在旁边，晚点再回来就好。这一层还有些地方没看过，先去绕绕吧。
dialogue.player = 天狐：“好想喝饮料……冰的。”
status = 口渴 2
floor.progress = 7/7
```

之后进入新的探索场景，出口事件暂时结束；探索完再回到出口。

不可把“先不走”记成：

```text
path.selected
junction
楼层切换
```

它是**出口事件内的一个行动**。

### 18.3 没有额外路可探索时

画面会出现：

```text
这一层再也找不到别的路了。要从哪里离开？
```

这是出口事件的**无额外路提示**，不是普通路口。

```text
exit.promptNoMore = 这一层再也找不到别的路了。要从哪里离开？
```

此时只剩真正的出口行动：

```text
- 推开那扇绿色的出口门
- 推开那扇还没装门把的门
```

### 18.4 出口选项可能带感知揭示

```text
推开那扇还没装门把的门
（只有你察觉到）你读过的资料里提过这种地方——这里通往 Level 0“大厅”。
```

这次不是模糊类型，而是**具体目的地揭示**：

```text
action.kind = exit_alt
action.hint = 你读过的资料里提过这种地方——这里通往 Level 0“大厅”。
action.revealedDestination = Level 0“大厅”
action.hintSource = 读过的资料 / 感知
```

仍要保留 hint 原文，不能只写目的地。

### 18.5 房间／场景列

```text
—— 房间：忽冷忽热 ——
```

或：

```text
—— 房间：还算正常 ——
```

分类：

```text
scene.name
```

这不是 `floor.header`，也不是 `event.name`。

### 18.6 出口事件中的进度

```text
出口进度 +1
出口进度 7/7
```

- 前者是本次事件完成的增量提示
- 后者是当前总进度
- 不要重复加总，也不要记成 8/7

### 18.7 出口事件完整状态

```text
exitEvent
  name = 出口的门
  actions[
    exit
    exit_alt
    explore_more
  ]
  ├─ 选 explore_more
  │    → result
  │    → 新探索场景
  │    → 探索事件
  │    → 回到出口
  │    → 再次显示出口选项
  └─ 选 exit / exit_alt
       → result
       → 系统结算
       → 下一层
```

## 19. 出口事件与普通事件的差异

| 项目 | 普通事件 | 出口事件 |
|---|---|---|
| 名称 | `【事件名】` | `【出口的门】` / `【光】` |
| prompt | `要怎么做？` | `要怎么做？`／`要从哪里离开？` |
| 行动 | 一般行动 | 真出口／替代出口／先不走 |
| 是否可延后 | 不一定 | 可以，选 `explore_more` |
| 完成后 | 出口进度 +1 | 切到下一层 |
| 额外探索 | 楼层有上限 | 大多数楼层最多 2 个额外事件；Void 0 |

---

## 20. 修正第 16 节的“只有一个强制行动”

第 16 节的 `【光】` 仍然有效，但只代表 **The Void 这种没有额外事件的出口**。

一般楼层的出口事件要按第 18 节处理：

```text
event.kind = exit
event.actions 可以有多个
其中一个是 explore_more
```

不可再把“出口事件只有一个行动”写成全域规则。

## 21. 出口 → 新楼层的边界实例（Level 27“木之荒芜”）

画面顺序：

```text
scene.end =
这一间的灯是亮的，门是好的，温度刚刚好。难得。
你绕来绕去，最后只剩下出口。

exit.action.selected =
→ 你决定：“推开那扇绿色的出口门”

exit.result =
门后面是一条木头的走廊，又旧又暗，墙板发黑，地板嘎吱嘎吱响。墙的后面，好像有人在敲。

system.transition =
(走出了这一层——这段路的记忆留了下来：你的记忆碎片 +4)
已经走过 5 层了——你：经验 +5

floor.header = —— Level 27“木之荒芜”——

floor.intro =
木头。墙是木板、天花板是木板、地上是木地板，铺著一条灰灰的地毯。
木头很旧，旧得发黑，有些地方烂得软软的，一按就陷下去。空气很闷，灰尘在昏暗的灯光里慢慢地飘。
天狐咳了一声，又咳了一声。
墙的后面，好像有人在轻轻地敲。叩、叩、叩。

dialogue.player =
天狐：“咳……好多灰尘……”

junction.text =
一条弯弯曲曲的木头走廊，地板每踩一步就吱一声。

junction.prompt = 要走哪条路？
junction.paths = [
  { text: 走进一间比较干燥的木头房间, perception: false },
  { text: 往那块地毯鼓起来的地方走, perception: false }
]
```

规则：

- `exit.result` 虽然描述“木头走廊”，仍然是出口事件结果，不是 `floor.intro`。
- 新楼层从 `—— Level 27「木之荒蕪」——` 才开始。
- 第三人的角色动作描写（`天狐咳了一声`）可以留在 `floor.intro`，但角色台词（绿色 `天狐：“…”`）要另外记 `dialogue.player`。
- 出口结果与新楼层介绍可能有相似意象（都提到墙后有人敲），但**不是同一句**，不要跨段去重。
- `第 6 層` 是本局楼层计数；`Level 27` 才是楼层 id。
- 新楼层介绍后、`要走哪条路？` 前的那句白字是 `junction.text`，不是 `floor.intro`。

## 22. 事件本身造成楼层切换（没有出口事件）

并非所有楼层切换都会先出现 `【出口的门】`、`【光】` 或 `出口进度`。

事件结果可以直接把玩家送到另一层。

### 22.1 实例：`【地上的洞】` → `Level 2.1「地下綜合體」`

```text
event.name = 地上的洞
event.intro =
地毯的正中央有一个圆圆的洞，边缘很整齐，像是用尺画出来的。往下看，什么都看不到，丢一片碎纸下去，听不到落地的声音。
洞旁边，有人用原子笔写著：“许愿池。一次一枚。”

action.selected =
→ 你决定：“丢一枚硬币下去，许个愿”

event.result =
……但接下来发生的事，谁也没有料到。
硬币掉下去之后，洞开始慢慢变大。地毯往洞里滑，你也往洞里滑——等你回过神来，四周已经是完全陌生的地方了。

event.result.effect.floorTransition = Level 2.1“地下综合体”

system.transition =
(走出了这一层——这段路的记忆留了下来：你的记忆碎片 +5)
已经走过 6 层了——你：经验 +6

floor.title = Level 2.1“地下综合体”
floor.meta  = 第 7 层｜岔路
floor.header = —— Level 2.1“地下综合体”——

floor.intro =
你从一面滚烫的墙里跌出来，跌进一片昏暗的迷宫。墙、天花板、柱子全是水泥砖砌的，砖缝里填著像水泥又像胶水的东西，怎么抠都抠不动。
灯光很少：几颗昏黄的小灯泡、几盏肮脏兮兮的工业灯，偶尔还有插在墙上的火把。地上一半是泥土，一半是水泥，到处是松脱的钢筋。
远处有水滴声，还有很低很低的机器嗡嗡声——那个声音，不管你怎么走，都不会变近。

dialogue.player = 天狐：“火把的影子……好像多了一个……”

junction.text =
一条笔直的走廊，你走了五分钟，走到了……刚才出发的地方。一个转弯都没有。

junction.prompt = 要走哪条路？
junction.paths = [
  { text: 走进那个天花板垂著一根根水泥柱的洞窟, perception: false },
  { text: 走进那条墙面特别粗糙的窄道, perception: false },
  {
    text: 跟著火把走,
    perception: true,
    hint: （只有你察觉到）你听见那边有很慢很慢的流水声。,
    hintKind: 流水声,
    announce: true
  }
]
```

### 22.2 规则

```text
event.kind = transition_event / floor_jump
event.result.causesFloorChange = true
event.result.nextFloor = Level 2.1“地下综合体”
```

- 事件本身可以是楼层切换来源。
- **不强制**先有出口事件。
- 不一定要出现“出口进度”。
- 系统结算（记忆碎片、经验）可以直接接在事件结果后。
- 新楼层从 `floor.header` 才开始；`event.result` 不是 `floor.intro`。

### 22.3 不可假设切层一定有提示

```text
楼层切换
  ├─ 出口事件（【出口的门】/【光】）
  └─ 事件结果直接切层（【地上的洞】）
```

Parser 不能只在看到出口事件时才准备切层；任何事件结果后都可能出现：

```text
system.transition
→ floor.header
```

### 22.4 小数楼层

```text
Level 2.1“地下综合体”
```

不是 `Level 2` 的子事件，是一个独立楼层 id：

```text
floor.id = 2.1
```

`第 7 層` 仍是本局楼层计数，不是 `Level 7`。

### 22.5 感知提示仍只记类型

```text
跟著火把走
（只有你察觉到）你听见那边有很慢很慢的流水声。
```

只能记：

```text
path.perception = true
path.hint = 你听见那边有很慢很慢的流水声
path.hintKind = 流水声
```

不可自行补成“水相关事件”或某个事件名。

## 23. 战斗切入与高速取样需求

### 23.1 战斗是路径选择的结果

画面顺序可能是：

```text
path.selected =
→ 你决定：“走进那个天花板垂著一根根水泥柱的洞窟”

combat.lead =
前面那盏工业灯，突然开始变亮。

combat.start =
【战斗】巨大的光附灵
```

战斗不是独立凭空出现；它通常由**上一个路口选择**触发。

因此每场战斗都要尝试记录：

```text
combat.trigger.kind = path
combat.trigger.text = 走进那个天花板垂著一根根水泥柱的洞窟
combat.trigger.frame = 选择时的 frame id
```

如果取样漏掉那个路口，不能乱猜，要标：

```text
combat.trigger = unknown
combat.trigger.reason = text_missed
```

### 23.2 战斗画面可读出的字段

```text
combat.enemy.name = 巨大的光附灵
combat.enemy.hp = 23/23
combat.enemy.defense = 14
combat.initiative = 巨大的光附灵 13 → 天狐 10
combat.round = 第 1 回合
```

战斗开场介绍：

```text
你一靠近那盏灯，灯就开始变亮——亮到刺眼、亮到发烫、亮到整条隧道只剩白色。灯里面有东西。
光附灵是没有怪东西的东西，它们附身在光源上，先用强光把人照得头昏眼花，再发动攻击。一般的攻击很难伤到它。你注意到，它好像离不开有灯的地方。
巨大的光附灵：比一般的大上一圈
```

这是 `combat.intro`，不是楼层介绍。

战斗进入检定：

```text
（魅力 难度 18）天狐 掷出 1+1=2 → 大失败！ 理智 -6
```

分类：

```text
combat.entryCheck.attribute = 魅力
combat.entryCheck.outcome = failure
combat.entryCheck.effects = [{ kind: 理智, amount: -6 }]
```

同样**不记录实际难度与骰值**。

先攻顺序：

```text
combat.initiative = 巨大的光附灵 13 → 天狐 10
```

敌人行动：

```text
（巨大的光附灵 灼烧 防御 13）巨大的光附灵 从灯泡里窜出一道炽热的光，扑向 天狐：掷出 15+6=21 → 命中 天狐！ 体力 -7、理智 -2
```

分类：

```text
combat.enemyAction.name = 灼烧
combat.enemyAction.target = 天狐
combat.enemyAction.outcome = hit
combat.enemyAction.effects = [{ kind: 体力, amount: -7 }, { kind: 理智, amount: -2 }]
```

玩家行动面板：

```text
攻击
技能
防御／闪避
切换武器
使用物品
逃跑
```

分类：

```text
combat.playerActions[]
```

### 23.3 目前的取样速度不足

目前的 `-Interval 0.8` 在实战中约只有 1.2 FPS；战斗文字可能在一帧内闪过，造成：

- 看不到是哪个路口选项触发战斗
- 战斗入场检定被漏掉
- 敌人先攻、第一回合文字被截断
- 结果与效果无法归属

### 23.4 必须加入的取样策略

1. **平常提高取样率**
   - 目标至少 2–4 FPS，必要时更高
   - 只做区域 OCR（main／opts／enemy／title），不要每帧整张 OCR

2. **战斗／转场爆发取样**
   - 检测到 `【战斗】`、`要怎么做？`、`要走哪条路？`、`出口进度`、`Level ???` 等锚点时
   - 立刻进入 burst：0.15–0.3 秒一张，持续 5–10 秒
   - burst 结束后回到一般取样

3. **环形缓冲（pre-roll）**
   - 记忆体保留最近 N 张画面／最近 N 次文字
   - 检测到战斗后，回头 OCR 战斗前几帧
   - 用来补回“哪个路口选项触发战斗”

4. **Last selected path**
   - 每次看到 `→ 你决定：“…”` 先更新 `lastSelected`
   - 若下一帧是 `【战斗】`，直接绑定：

```text
combat.trigger = lastSelected
```

5. **不确定就标 unknown**
   - 若 pre-roll 与 lastSelected 都没有，记 `trigger=unknown`
   - 不要用“最可能的选项”猜

6. **截图仍然只用来读字**
   - burst 截图只存在暂存
   - OCR 完成后删除
   - 不进 Wiki

### 23.5 战斗与事件的关系

目前先分开建模：

```text
event
  └─ combat
       ├─ enemy
       ├─ entryCheck
       ├─ initiative
       ├─ rounds[]
       │    ├─ enemyAction
       │    └─ playerAction
       └─ result
```

战斗是否算一个“事件”、是否占出口进度，目前**尚未由用户确认**，不要自行写入正式事件树。

### 23.6 不可自行补的战斗资料

- 未看到的路口选项
- 未看到的敌人 HP／防御
- 未看到的先攻顺序
- 未看到的伤害数字
- 未看到的战斗结果

宁可缺，不要编。

## 24. 战斗撤退与战后判定

这两张图是同一个战斗流程的后半：逃跑成功，回到路口。

### 24.1 战斗中的玩家行动

```text
combat.playerAction.kind = skill
combat.playerAction.name = 撤退路线
combat.playerAction.dialogue = 天狐：“论坛上说过，遇到这种要跑！往这边！”
combat.playerAction.text = 天狐 指出了一条退路。
```

接著是撤退判定：

```text
combat.escape.check.attribute = 敏捷
combat.escape.check.outcome = success
combat.escape.result = 天狐 撤离了战斗。
```

不记：

```text
难度 9
9+9=18
```

### 24.2 战斗结束

```text
combat.result =
你一路狂奔，直到再也听不见身后的声音。
战斗结束了——你活了下来，但什么也没拿到。

combat.outcome = escaped
combat.loot = 无
```

### 24.3 战后判定

战斗结束后还可能出现额外判定：

```text
combat.aftermathCheck.attribute = 智力
combat.aftermathCheck.outcome = success
combat.aftermathCheck.text =
天狐 皱起眉头：“刚才光附灵的动作……好像有什么规律，可是还抓不太到。下次再遇到，要仔细看。”
combat.aftermathCheck.flag = 下次再遇到也许就想得通
```

这不是事件行动，也不是战斗攻击；是**战后观察／情报判定**。

### 24.4 战斗后回到路口

```text
combat.completed
→ floor.progress = 1/8
→ 新路口
```

新路口：

```text
floor.progress = 1/8

statusEffect =
天狐 渴得嘴唇干裂，眼前一阵阵发黑。体力 -1、理智 -1

junction.text =
一根比较冷的管子贴著天花板经过，管子上凝结著一颗颗水珠，闻起来是杏仁的味道。

dialogue.player =
天狐：“我、我还可以……只是流了一点血。”

junction.prompt = 要走哪条路？
junction.paths = [
  { text: 穿过满是岩石阴影的洞窟, perception: false },
  { text: 往机器声的方向走, perception: false }
]
```

### 24.5 战斗与出口进度的关系

截图显示战斗撤退后出现：

```text
出口进度 1/8
```

但“战斗是否算一个事件、是否一定占出口进度”目前**尚未由用户确认**。

先保留：

```text
floor.progress.current = 1
floor.progress.total = 8
floor.progress.source = unknown（可能是战斗／路线事件）
```

不要自行写成“战斗一定算事件”。

### 24.6 状态效果

```text
天狐 渴得嘴唇干裂，眼前一阵阵发黑。体力 -1、理智 -1
```

分类：

```text
statusEffect.target = 天狐
statusEffect.reason = 口渴／脱水
statusEffect.effects = [
  { kind: 体力, amount: -1 },
  { kind: 理智, amount: -1 }
]
```

不可并进战斗伤害，也不可当成普通 dialogue。

### 24.7 高速取样补充

这一串文字全部可能在几秒内闪过：

```text
使用撤退路线
角色台词
指出退路
敏捷判定
撤离战斗
战斗结束
智力判定
战后台词
状态效果
出口进度
新路口文字
```

所以 pre-roll + burst 必须覆盖**战斗结束后 5–10 秒**，不能只在看到 `【战斗】` 时开始；否则会漏掉战后判定与出口进度。

## 25. 已确认：战斗算一个战斗事件

用户确认：

> 算一个战斗事件。

因此战斗不是独立于事件之外的东西，而是 `event` 的一种类型。

### 25.1 战斗事件模型

```text
event.kind = combat
event.header = 【战斗】巨大的光附灵
event.name = 巨大的光附灵

event.trigger =
  kind: path
  text: 走进那个天花板垂著一根根水泥柱的洞窟

combat = {
  enemy: {
    name: 巨大的光附灵,
    hp: 23/23,
    defense: 14,
    trait: 比一般的大上一圈
  },
  intro: ...,
  entryCheck: { attribute: 魅力, outcome: failure, effects: [...] },
  initiative: 巨大的光附灵 13 → 天狐 10,
  rounds: [...],
  playerAction: 撤退路线,
  escapeCheck: { attribute: 敏捷, outcome: success },
  result: 战斗结束了——你活了下来，但什么也没拿到。,
  outcome: escaped,
  aftermathCheck: { attribute: 智力, outcome: success, flag: ... }
}
```

### 25.2 战斗事件占一个事件进度

战斗事件完成后：

```text
event.completed
→ floor.progress.current += 1
```

例：

```text
战斗事件【巨大的光附灵】完成
→ 出口进度 1/8
```

所以之前截图的 `出口進度 1/8` 可以确定：

```text
floor.progress.source = combat_event
```

不是未知来源。

### 25.3 战斗事件的完成时机

一场战斗 = 一个事件，不是每一回合一个事件。

完成时机是整场战斗结束：

```text
胜利
或
成功撤退
```

战后判定（例如智力观察）仍属于同一场战斗事件，不另开新事件。

```text
combat.result
→ combat.aftermathCheck
→ event.completed
→ floor.progress +1
→ 下一个路口
```

### 25.4 战斗事件与普通事件的差异

| 项目 | 普通事件 | 战斗事件 |
|---|---|---|
| event.kind | normal | combat |
| 名称来源 | `【事件名】` | `【战斗】敌人名` |
| 内容 | intro / actions | enemy / combat rounds |
| 完成 | 看完按继续 | 胜利或撤退 |
| 进度 | +1 | +1 |
| 战后判定 | 不一定 | 可有，仍属同一事件 |

### 25.5 不可拆分

不可把以下拆成多个事件：

```text
路口选项
战斗开始
第 1 回合
第 2 回合
撤退
战后判定
```

它们全部属于**同一个战斗事件**：

```text
event.kind = combat
```

### 25.6 仍需保留的关联

```text
event.trigger.path
event.trigger.frame
event.completed
floor.progress
```

即使战斗文字闪得很快，也要靠 pre-roll / lastSelected 把“哪个路口触发这场战斗”补回来。

## 26. 第二场战斗事件：`【战斗】微笑梦魇`

### 26.1 入口

```text
path.result / combat.lead =
```

### 26.2 敌人资料

```text

combat.enemy.hp = 16/16
```

## 27. 结局／死亡流程（`全员迷失` / `全员逃离`）

这一组图不是普通事件，而是**本局结束**。

### 27.1 先出现战斗致死

```text
combat.damage =
命中 天狐！ 体力 -5、理智 -3

combat.defeat =
天狐 一直盯著黑暗里那排牙齿，盯到自己的嘴角也跟著慢慢往上弯……天狐 迷失了。
```

分类：

```text
combat.playerDefeated = true
run.outcome = missing
```

这场战斗事件到这里不会再回到普通路口，而是进入结局流程。

### 27.2 结局幻灯片

画面：

```text
全员逃离 / 全员迷失（原始标签，依画面照抄）
Level 2.1

机器的嗡嗡声还在远处，一点都没有变近。湿水泥河缓缓流过，把你留下的痕迹一点一点抹平。
```

第二张：

```text
后室不会记得任何人。
可是在“Level 2.1”的某个角落，有几个名字被很用力地刻进了墙里。每一个经过的人都会停下来看一眼，然后说：“他们走到这里了。”
```

分类：

```text
ending.kind = escape | missing | ...
ending.labelRaw = 画面上的原始标签
ending.floorId = Level 2.1
ending.slides[] = [
  { text: ... },
  { text: ... }
]
```

规则：

- 这是结局文本，不是 `floor.intro`
- `ending.labelRaw` 要保留画面原文
- 若同一局不同画面出现不同标签（例如 `全员逃离` / `全员迷失`），先保留两个 raw，不要自行合并
- `跳过` 是 UI，不是结局正文

### 27.3 角色墓志／最后讯息


这不是普通 `dialogue.player`；是结局角色卡／墓志。

### 27.6 标签不一致时

这组图中：

- 结局幻灯片标签看起来是 `全员逃离`
- 冒险结束卡是 `全员迷失`
- 战斗日志是 `天狐 迷失了`
- 死亡文字是 `【你迷失】`

先全部保留 raw：

```text
ending.labelSlide = ...
ending.labelSummary = ...
run.playerOutcome = missing
```

在确认之前，不要自行统一成单一结局名称。

### 27.7 结局与战斗事件的关系

流程：

```text
combat event
  → 玩家被击倒／迷失
  → combat.playerDefeated
  → ending.trigger
  → ending.slides
  → ending.epitaph
  → ending.summary
  → 回到大厅 / 再看一次结局
```

战斗事件仍然是战斗事件；但玩家死亡时，它同时是**本局结束的触发点**。

```text
event.kind = combat
event.completed = false
event.outcome = player_defeated
run.ending = missing
```

不要把它记成普通战斗胜利，也不要再记 `floor.progress +1`。
