# 记录器「已記錄／記錄編輯」UI 审查（2026-11-08）

> 审查对象：`客户端/ExpeditionRecorder.cs` 中 `RecordsForm`（已記錄窗口）与 `RecordEditForm`（右侧结构化编辑器）。
> 审查方式：反射加载**真实编译产物** `ExpeditionRecorder.exe`，在屏幕外实例化这两个窗体，按 1.0／1.6 字号、584／934／380／300 四种宽度渲染截图，并导出全部子控件的屏幕包围盒；另外跑了「改字号／改宽度／滚到底再拉伸」的行为探针。

## 0. 一句话结论

上一任做到的是**「单个控件单独调好，整套布局没有规则」**。

真正让右边缘看起来参差的不是某一个 `rightPad`，而是**同一个面板里有四套互不相干的宽度算法**：

| 式子 | 右端落在 | 距窗口右边缘 |
|---|---|---|
| 输入框 `AddRaw` | `PanelWidth() - 2` | 19px |
| 选项框 `AddOptionFrame` | `PanelWidth() - 8` | 25px |
| 标题 `AddHeading` | `14 + PanelWidth() - 28` | 31px |
| 配色预览 `AddPalettePreview` | `14 + min(520, …)` | **50px** |
| 樓層名称框 `AddFloorFields` | `252 + min(360, …)` | **31px** |
| 窄窗输入框 `AddRaw` narrow | `14 + avail - 28` | 31px |

而 `PanelWidth()` 本身又**无条件扣掉 17px 滚动条**——不管当前有没有滚动条。于是「翻到一条不需要滚动的记录」时，所有输入框会整体往左缩 17px（19px 空档 vs 2px 贴滚动条）。这一条就能解释用户截图里"同一条记录、右边缘参差"的大半观感。

同一条 584px 宽的面板，这是**没有滚动条**时的样子——输入框离右边还剩一整条 19px 的空带（`04-物品-无滚动条.png`）：

![物品记录：无滚动条时右侧空出 19px](<2026-11-08-UI审查/04-物品-无滚动条.png>)

有滚动条时同一位置只剩 2px（`02-事件-选项框.png`），对比着看最明显。

## 3. 问题清单

### P0 — 直接造成"参差"和"错位"的

#### P0-1　`PanelWidth()` 无条件扣 17px，右侧留白在 2px 与 19px 之间跳

- **现象**：翻记录时，右边缘一会儿贴着滚动条，一会儿空出 19px。
- **实测**：
  - 事件（内容溢出、有滚动条）：面板客户区 **567**，字段右端 **565** → 距滚动条 2px。
  - 物品／出口／商店（内容不溢出、无滚动条）：面板客户区 **584**，字段右端仍是 **565** → 距窗口右边 **19px**。
- **根因**：`PanelWidth()`（3816-3820）永远减 `VerticalScrollBarWidth`，而滚动条只在溢出时存在。
- **改法（两条路，选一条，不要混）**：

  **路线 1（推荐）：用真实客户区宽度，并在滚动条出现/消失时重排一次。**

```csharp
int PanelWidth() { return Math.Max(UiScale.Px(180), _panel.ClientSize.Width); }

// 构造里补一行：滚动条出现/消失会改客户区宽度，SizeChanged 不会触发，
// 必须用 ClientSizeChanged，否则字段会压到滚动条底下 17px。
_panel.ClientSizeChanged += delegate { QueueRelayout(); };
```

  实测该值：有滚动条时 567、无滚动条时 584，正好是"当下真能用"的宽度。**不要**再自己减滚动条——WinForms 已经扣过了。
  这样字段离"看得见的右边界"永远是同一个距离，翻记录不会跳。

  ⚠️ 两个坑：
  - `RelayoutFields`（4815 行）有 `Math.Abs(w - _lastPanelWidth) < 24` 的阈值，而滚动条开合只差 17px，**正好被它吃掉**。要在 `ClientSizeChanged` 里把 `_lastPanelWidth` 置 `-1`（或单独比较 `VerticalScroll.Visible` 是否变化）强制重排一次。
  - 滚动条是被内容高度"撑"出来的：重排会改高度，可能又让滚动条消失，来回抖。重排时请保留滚动位置（见 P1-4），并只在 `Visible` 真变化时才重建。

  **路线 2：保留"永远预留 17px"，但把它做成看得见的 gutter。**

  代价是：没有滚动条时右边会空出 31px。要让它不显脏，就得给这块空白一个视觉交代——面板右侧画一条 `Px(17)` 宽、颜色比 `Surface` 深一档的竖条（或一条 1px 分隔线），并且**所有表单、所有类都按同一个式子算**（见 P0-2）。现在的实现是这条路线的半成品：预留了，却没交代，别的类也不遵守。

#### P0-2　四个类各有一套右端算法

- **现象**：输入框、选项框、标题、配色预览、樓層名称框右端全部不同（565/559/553/534）。
- **根因**：
  - `AddRaw`（3856-3859）：`rightPad` 默认 `Px(2)`；
  - `AddOptionFrame`（3752-3754）：`x = 8`、`w = avail - 16`；
  - `AddHeading`（3741）：`14 + PanelWidth() - 28`；
  - `AddPalettePreview`（4523）：`min(520, …)`；
  - `AddFloorFields`（4380）：名称框 `min(360, …)`。
- **改法**：只留一套"页面盒子"，所有方法都从它取数（见第 4 节）。

#### P0-3　字号 1.6 倍时，靠测量文字算出来的宽度被乘了两次

- **现象**：1.6 字号下，"事件類型"下拉被拉得很宽（178px，实际只要 ~126px），六个「屬性檢定」按钮从 47px 变成 108px，一行几乎占满。
- **实测**：1.6 字号下 `DarkComboBox` 宽 **178**；按 14.4pt 文本 89px 算，正确值约 126。
- **根因**：
  - `ComboWidth()`（4274）：`TextRenderer.MeasureText(s, Font).Width * UiScale.Scale` —— 此时 `Font` 已经被 `UiScale.Apply()` 放大过，再乘一次；
  - `AddChoice()`（4230）：`tw = MeasureText(texts[i], Font).Width * UiScale.Scale`，同样双重放大。
  - 只有 `FieldLabelWidth()` / `AddOptionFrame()` 用了"基号字 × Scale"，所以那两处是对的。
- **为什么 1.0 看不出来**：Scale=1 时乘不乘都一样；而且**每条记录第一次显示时其实建了两遍**（见 P1-4），第二遍才吃到这个 bug。
- **改法**：统一一个测量入口，只在这里乘 Scale：

```csharp
static int TextW(string s, float basePt, FontStyle st = FontStyle.Regular) {
    using (var f = new Font(UiText.FontFamily, basePt * UiScale.Scale, st))
        return TextRenderer.MeasureText(s, f, new Size(int.MaxValue, int.MaxValue),
            TextFormatFlags.NoPadding | TextFormatFlags.SingleLine).Width;
}
```

  然后把 `ComboWidth`、`AddChoice`、`AddOptionFrame` 的 `capW`、`AlignFieldLabel` 全部改成调用它。

  1.6 字号实测（`06-事件-1.6倍字号.png`）：「事件類型」下拉 178px 宽、六个屬性檢定按钮一颗 108px，而按文字宽度本应约 126px / 75px。

  ![1.6 倍字号：下拉与按钮被双重放大](<2026-11-08-UI审查/06-事件-1.6倍字号.png>)

#### P0-4　多行文本框高度按 15px/行算，控件实际是 16px/行

- **现象**：长介绍、长结果最后一行压在边框上，甚至被吃掉。
- **实测**（同一控件内自量）：
  - 3 行介绍：`h = 49`；控件行距 `GetPositionFromCharIndex` 显示第 3 行在 y=32、`Font.Height = 16` → 需要 32+16+2 = **50**。
  - 4 行介绍：`h = 64`，需要 **66**。
  - 规律：`h = 行数 × 15 + 4`，而实际是 `行数 × 16 + 2` → 差 `行数 − 2`：**每多一行多欠 1px**。8 行少 6px，16 行少 14px（整整一行滚到框外）。
  - `ScrollBars = None`（3863），被吃掉的文字**看不到也滚不到**。
- **根因**：`WrappedHeight`（3885-3893）和 `ExactTextHeight`（3895-3900）都用 `TextRenderer.MeasureText("国", font).Height`（15），而不是 TextBox 自己的行距（`Font.Height`，16）。
- **改法**：

```csharp
int ExactTextHeight(TextBox t) {
    if (string.IsNullOrEmpty(t.Text)) return t.Font.Height + UiScale.Px(8);
    int last = t.GetPositionFromCharIndex(t.TextLength - 1).Y;
    return last + t.Font.Height + UiScale.Px(8);   // 8 = 上下内边距 + 边框
}
```

  `WrappedHeight` 只用 `Font.Height * 行数 + Px(8)`。改完要测 3／8／20 行、末尾带 `\n`、空文本。

#### P0-5　「已記錄」列表是系统默认样式：选中是亮蓝 #0078D7

- **现象**：深色界面里选中一条记录，整行变成 Windows 经典亮蓝（实测像素 `0,120,215`），和整套配色完全冲突；标题过长时直接硬切（`HorizontalScrollbar = true`，底部多一条横向滚动条）。
- **根因**：`_list` 是普通 `ListBox`（4981-4989），没设 `DrawMode`；条目是 `Kind + "　" + Title + "　" + Time`（5181），靠全角空格对齐，时间列长短不一。
- **改法**：`DrawMode = OwnerDrawFixed` + 自绘三列（类型 44px／标题省略号／时间右对齐），选中色用 `Color.FromArgb(46, 74, 110)`；关掉 `HorizontalScrollbar`，改用 `TextRenderer` + `EndEllipsis`。条目文字拆成三个字段传，不要再拼字符串。

  ![已記錄窗口：选中是系统亮蓝，标题硬切](<2026-11-08-UI审查/01-已記錄窗口-默认.png>)

### P1 — 明显的观感问题

#### P1-1　标签与字段之间 19px（≈1.6 个字），不是交接文档说的"一个字宽"

- 实测 `FieldGap() = 19`，标签右端 79、字段左端 98。
- 根因：`FieldGap()`（3832-3836）用 `TextRenderer.MeasureText("国", font).Width`。实测中文字宽是 12px（"国国"=31、"国国国"=43），但单字测量带 7px 内建 padding → 19px，于是"一个字宽"变成了 1.6 个字宽。
- 附带一个隐藏问题：`FieldLabelWidth()` 已经按「⭐條件選項」+ 一个字算好了宽（65+19=84），`AlignFieldLabel()`（3838-3842）又减掉 `FieldGap()` 得到一个**比最长标签还窄**的 65px 框——「⭐條件選項」实测正好 65px，**零余量**；「效果（每行一条）」「商品（每行一条）」已经在换行并被切（见 `04-物品-无滚动条.png`）。
- 改法：

```csharp
int FieldGap() => UiScale.Px(10);
int FieldLabelWidth() => TextW("⭐條件選項", 9F) + UiScale.Px(6);
void AlignFieldLabel(Label l, int w) { l.Width = w; l.TextAlign = ContentAlignment.MiddleRight; }
```

  （即：**标签列宽只定一次，不再在摆放时二次扣减**。）

#### P1-2　标签文字比字段文字低 2~3px

- 实测：标签 `Top = 行首 + 3`、高 22；字段 `Top = 行首`、高 23。控件内居中后文字中心差 2.5px。
- 放大 `02-事件-选项框.png` 左上角能直接看出来：「事件名」比「绿色的小人」低一档。
- 改法：标签与字段同 `Top`、同高，或统一 `l.Top = t.Top; l.Height = t.Height;`。

#### P1-3　樓層／類型／主題 用了第二套左列（90px、左对齐、固定 x）

- 实测 `AddFloorFields` 的标签宽 `Px(90)`、**默认左对齐**（4328），`AddThemeButtons` 同样（4483），按钮固定放在 x=108 / 214（4335、4342、4489、4495）。
- 结果：事件/物品/出口/結局/商店 的标签是"右对齐到 79"，樓層表单的标签是"左对齐到 14"，同一窗口里两种排版。
- 顺带：`AddRestTag`（3951-3976）**没有窄窗分支**，其余字段都堆叠了，只有「休息處」还是左右排。
- 改法：樓層/主題/類型 全部改用 `FieldX`；窄窗统一走同一个 `Layout.IsNarrow` 分支，不要每个方法各写一遍。

#### P1-4　每条记录第一次显示会建两遍，且拉伸窗口后滚动位置归零

- 实测：先把面板滚到底（`Y = -173`），再把窗口拉宽 60px → `AutoScrollPosition` 回到 `(0,0)`，并且焦点丢失。
- 根因：`_lastPanelWidth` 初值 0（3621），`RelayoutFields`（4811-4837）第一次必然触发（`|w-0| ≥ 24`），把整棵控件树清掉重建；重建没有恢复滚动位置，也没有恢复焦点。
- 双重后果：①每条记录多建一遍（P0-3 的双重缩放就是在这第二遍里暴露的）；②用户拉一下窗口就跳回顶部。
- 改法：
  1. 构造完 `BuildFields()` 后设 `_lastPanelWidth = PanelWidth()`，掐掉无意义的首轮重建；
  2. 重建前存 `_panel.AutoScrollPosition` 和 `ActiveControl` 的标识，重建后还原。

#### P1-5　ComboBox 高度不随字号走，1.6 倍时文字被压

- 实测 1.6 字号：`DarkComboBox` 仍是 **26px 高**（`SetBounds` 给的 42 被 WinForms 忽略，ComboBox 高度由字体决定），而字体行高已经 26px → 文字几乎顶满、上下被切。
- 同时标签高 35、字段高 26，行内基线再差 7px。
- 改法：不要给 ComboBox 设高度；用 `cb.Height = cb.PreferredHeight`（或干脆用 `PreferredHeight` 参与 `_y` 累加），并把 `AddComboField`/`AddConditionRow` 的行高改成 `Math.Max(UiScale.Px(26), cb.PreferredHeight)`。

#### P1-6　「選項 N」框：嵌套框左边线完全重合，右边线又不齐

- 实测：外层框 `X=8,W=551`，内层「選項 N 結果」框也是 `X=8,W=551` → **左边线画在同一条像素上**，内层只多一条上边线；观感是"一个盒子被横线切开"，看不出层级。
- 右边线在 559，比字段 565 内缩 6px；窄窗时反过来，框右边 355 比字段 349 **多出** 6px。
- 标题「選項 N」从 x=18 开始，于是上边线在 x=8~18 留了一个 10px 的**断头**（截图里能看到一截悬空的线头）。
- 改法（任选其一，推荐 A）：
  - **A. 只画外框**：结果区不再画矩形，改成在选项框内加左侧 2px 强调条 + 缩进 `Px(10)`，层级一目了然；
  - **B. 画嵌套但错开**：内框 `X = 外框.X + Px(10)`、右边 = 外框右边 − `Px(10)`，用更暗的线色；
  - **C. 标题遮罩做成"缺口"**：画上边线时分两段画，跳过 `[cap.Right + Px(4), ∞)` 之前的部分，别再用 Label 背景去盖。

### P2 — 一致性／健壮性

#### P2-1　窗口没有最小尺寸，拉小后整块编辑区溢出到窗口外

- 实测 300×400：右侧编辑器右端跑到 **x=387**（窗口只有 300），`dR = -87`；「關閉」按钮被切掉；内层面板还冒出了**横向滚动条**（`hScroll=True`），和 `ShowNativeScroll()` 想关掉它的意图相反。
- 根因：`RecordsForm` 没设 `MinimumSize`；`LayoutRecords`（5048-5084）里 `detailW = Math.Max(Px(220), …)`、`maxW = Math.Max(minW, …)` 这些下限会把控件顶出窗口；`AddRaw`（3857）等处的 `Math.Max(Px(120/180/220), …)` 同理。
- 改法：① `MinimumSize = new Size(Px(640), Px(420))`；② 下限只用于"内容滚动区"，不要用于"窗口内几何"——宽度一律 `Math.Max(0, 可用宽度)`，宁可挤也不要溢出。

  ![300×400：编辑区溢出到窗口外，底部按钮被切](<2026-11-08-UI审查/08-已記錄-300px.png>)

#### P2-2　内外两层滚动容器，右侧出现"双边框 + 双滚动条"

- `_editorHost`（4991-4997）`AutoScroll = true` + `BorderStyle.FixedSingle`，里面又塞了一个自带 `AutoScroll` 的 `RecordEditForm`。
- 实测：宿主 585 宽，内层面板 568 + 17 滚动条，字段右端 788，宿主右边框在 807 → 右侧是「滚动条 → 2px → 双边框」。
- 改法：宿主 `AutoScroll = false`、去掉 `BorderStyle`（或只保留一个）。

#### P2-3　滚轮钩子用屏幕矩形判断，没考虑窗口被遮挡

- `PanelMouseWheelHook`（2200-2245）用 `_panel.RectangleToScreen(...).Contains(sp)` 判断「鼠标在面板上」。低级鼠标钩子拿不到 z-order：如果记录窗口被别的窗口（游戏/浏览器）盖住，在**被盖住的区域**滚滚轮，底下这个面板照样滚，事件还被 `return 1` 吞掉。
- 另外每个编辑器实例都装一个 `WH_MOUSE_LL`，列表切换一次就装/卸一次（关闭路径有 `OnFormClosing` 卸载，不算泄漏，但频繁装卸）。
- 改法：改成 `WindowFromPoint(sp)` → `Control.FromChildHandle(hwnd)`，判断是否为本面板的后代；或者删掉钩子，改为在 `Panel` 上重写 `WndProc` 处理 `WM_MOUSEWHEEL`（子控件不吃的滚轮会冒泡到父窗口）。

#### P2-4　滚动条外观：17px 槽里只有 2px 的拇指

- 实测像素：槽 `(23,23,23)`，拇指是 `x=575..576` 的一条竖线、`y=17..313`（Windows 11 深色细滚动条）。17px 的槽有 15px 是空的，和左侧紧凑的字段区不搭。
- 交接文档已经点出"要么彻底用系统滚动条、要么自己画"，现在两头都留着：原生滚动条在用，`DarkScrollBar` 还挂在同一个坐标上（只是 `Visible=false`），下次谁改一行 `Visible=true` 就会两条叠在一起。
- 建议：**选一条路**——
  - 路线 A（省事）：留系统滚动条，只修 P0-1 的宽度计算，接受细拇指；
  - 路线 B（要观感）：`AutoScroll = false`，自己做 viewport（`Location` 偏移 + 自绘滚动条 + `MouseWheel`），然后把 `DarkScrollBar` 真正接上。**不要**再走"隐藏原生滚动条 + 调 `AutoScrollPosition`"这条已经证明无效的中间路线。

#### P2-5　边框／强调色没有 token，四种灰混用

- 现在出现的边框色：`105,108,118`（选项框）、`78,78,84`（按钮）、`130,170,215`（选中）、`SystemColors`（TextBox `FixedSingle`）、`#0078D7`（列表选中）。
- 建议一套 6 个 token：`Surface #202024`、`Field #28282C`、`Border #4E4E54`、`BorderStrong #6A6D76`、`TextDim #AAAAB2`、`Accent #FFD678`、`Ok #50A05A`，全部走常量。

### P3 — 设计层面（不是像素 bug，是结构问题）

这五条不是"改一个数值"，但决定了这套界面能不能长期用下去。

1. **没有分区标题，一眼看不出结构。**
   事件编辑器现在是「基础字段 → 選項 1 → 結果 → 選項 2 → …」一路平铺，唯一的层级手段是那圈灰线。实测一条 4 选项的岔路事件，内容高约 **888px**、视口 446px，要滚两屏才能看完，中途很容易分不清自己在哪个选项里。
   建议：`事件信息`／`選項 N`／`結果` 做成三级标题（加粗 + 上下各 `Px(8)` 留白），框线只留给"选项块"这一级。

2. **右栏没有身份栏。**
   内嵌编辑时窗体标题（"編輯記錄：事件"）是看不见的，用户不知道右边这条到底对应左边哪一行。
   建议：右栏顶部固定 `Px(32)` 高的 header：`事件 · 绿色的小人`，右侧放保存状态。

3. **自动保存没有反馈。**
   600ms 防抖自动写盘（`SaveData`），但界面上没有任何"保存中／已保存"的提示，用户只能靠"没弹错误"来推断。
   建议：header 右侧一个状态点 + 时间（`已保存 18:24`／`未保存`），失败时变红。

4. **空值没有占位。**
   空的「結果 3」「選項說明」就是一条黑框，分不清"这条本来就没有"和"没读出来"。
   建议：多行框为空时画灰色 `（未填寫）`，获得焦点或输入即消失；只做视觉，不写进数据。

5. **默认宽度偏窄，密度偏松。**
   默认 820 宽 → 右栏只有 585px，而 9pt 字下一行能放约 36 个汉字；一条普通事件就要滚两屏。同时每行 28~32px、控件 22~26px，屏幕利用率不高。
   建议：`RecordsForm` 默认宽度提到 `1040`（或记住上次尺寸）；左列表最小宽度降到 180，把空间让给编辑区；行距保持，靠分区标题来分隔，而不是靠留白硬撑。

## 4. 建议的统一布局规则（可直接落地）

### 4.1 常量（放进 `RecordEditForm` 顶部或独立 `EditorLayout` 类）

```csharp
int Px(int v) => UiScale.Px(v);

// 页面盒子：所有字段、框、标题、预览都从这四个数推，禁止各方法自算
int PageLeft   => Px(14);
int PageRight  => Px(14);
int LabelW     => TextW("⭐條件選項", 9F) + Px(6);   // 只算一次，构造里缓存
int LabelGap   => Px(10);
int FieldX     => PageLeft + LabelW + LabelGap;
int FieldRight => _panel.ClientSize.Width - PageRight;   // 真实可用宽（P0-1）
int FieldW     => Math.Max(Px(120), FieldRight - FieldX);

// 行距
int RowGap     => Px(6);
int FieldH     => Px(24);
int ButtonH    => Px(26);

// 选项框
int FrameInset => Px(6);      // 相对页面盒子向外扩
int CapInset   => Px(8);
```

### 4.2 一条硬规则

> **任何控件宽度只能由 `FieldX / FieldRight` 推导；`360`、`520` 这类"绝对上限"一律删掉——需要窄的元素用 `Math.Min(FieldW, 内容宽度)`，其余一律用满 `FieldW`。**

- `AddHeading`：`SetBounds(PageLeft, y, FieldRight - PageLeft, h)`
- `AddPalettePreview`：`w = FieldW`（去掉 520 上限）
- `AddFloorFields` 名称框：`w = FieldRight - nameX`（去掉 360 上限）
- `AddOptionFrame`：`x = PageLeft - FrameInset`，`w = FieldRight - x + FrameInset`
- `AddRaw` 窄窗：`w = FieldRight - PageLeft`（不要 `- Px(28)`）

### 4.3 窄窗只有一个开关

```csharp
bool Narrow => FieldW < Px(360);   // 原来各方法里的 430/220/180 阈值统一
```

`Narrow` 为真时：标签独占一行、字段占满 `PageLeft..FieldRight`；`AddRestTag`、`AddThemeButtons`、`AddFloorFields` 都走同一分支。
