**看结果只需要一个文件**：`wiki/_incoming/<场次>/auto-import.json`
里面 `imported`、`events.added`、`events.rejected` 就是这一场的成绩。

# 第二轮（17:59 那轮）

## 7. 覆盖率从一半拉到 2/3

诊断结果推翻了我之前的判断：**不是记录器丢帧，是管线自己把好的事件扔了。**

`events.bound.jsonl` 里这一场解析出 24 条事件（0 层 15 条全覆盖），
但 `cleanEvent` 只放行 11 条。逐条查原因后修了三处：

| 原因 | 例子 | 修法 |
|---|---|---|
| `cleanActions` 在去重**之前**就砍掉 >4 条 | 「家具留下的痕跡」6 条变体（其实只有 3 个真选项） | 原始上限放宽到 8，去重后再要求 2–4 |
| 选项里混着道具标签与门槛行 | `★「工地安全帽」`、`★力量4+` | 去 ★ 后按道具标签／属性门槛过滤 |
| OCR 形近字让选项整组失效 | `櫃冂掰開`（冂=門）、`不妻動`、`眶知難` | 进 `ocr-fix.mjs` 已知错字表 |

结果：0 层 7→**10**、1 层 3→**4**，共 14 条事件。

## 8. 路口（junction）从 0 补到 4

现在会写进各层 `events.json` 的 `junctions`（模板早就有渲染代码）：

场景若只剩对话残片就退回提问文字、路径沿用 `cleanActions` 的同一套去重。

## 12. 重要更正：`progress.total` 不是「事件数」

上一节说「0 层还差 5 条」，深入查了帧级数据后**这个说法要修正**：

把 24 条事件覆盖的帧区间和「要怎么做」提示出现的帧对了一遍，发现没被解析成事件的
7 个提示画面**全是战斗／转场**（「第 2 回合」「命中！造成 10 伤害」「走出了这一层」）。
对照进度编号也对得上：`6/15` 是「商店」、`8/15` 出现了两次。

所以 `progress.total = 15` 是**这一层的节点总数**（事件＋战斗＋商店＋转场），
不是事件数。10/15 不代表「少了 5 个事件」，实际上缺的大多是刻意不记录的战斗节点。

已做的处理：

- 站点横幅改口径：「有節點沒記錄到……戰鬥、商店不算事件，所以進度條上的數字（例如 10/15）不會等於事件條數」
- 没有把 `combat` 绑到事件上：模板的事件卡片根本不渲染 `e.combat`，
  要显示得先改模板，风险比收益大，留到有实玩数据再做。

结论：**覆盖率这个指标本身不可靠，不要再拿它当验收标准。**
真正可信的是 verify-final 的那些结构检查（名字干净、selected ∈ actions、路口 2–4 條、
收不齐必须标 partial）。

# 第三轮（19:52 复核）

## 13. 复核发现的一个真问题：`difficulty: "variable"`

`event-parse.mjs` 的 `addCheck()` 把检定难度固定写成字符串 `'variable'`：

```js
obj.check.difficulty = 'variable';   // ← 永远这样
```

也就是说「不知道难度」被写成了一个看起来像值的占位字。4 条事件带着它进了正式库
（被丟棄的東西、可以上鎖的小辦公室、家具留下的痕跡、褪色的壁紙）。

同一行代码里其实已经拿到了原始字串，只是没去解析里面的数字。修法：

```js
const dc = String(s).match(/(?:難度|难度)\s*[:：]?\s*(\d{1,2})/);
if (dc) obj.check.difficulty = Number(dc[1]);   // 读不到就干脆不写这个字段
```

重建后的实际结果：

```text
被丟棄的東西        感知 難度 12  成功
可以上鎖的小辦公室   感知 難度 12  成功
家具留下的痕跡      智力 難度 11  失敗
褪色的壁紙          感知 難度 13  失敗
```

`difficulty:"variable"` 在 content 里现在是 0 处。

# 第四轮（21:50）：linecrops 空间与耗时

## 15. 实测（会话 backroom-20261029-212222，11 分钟）

| 项 | 数值 |
|---|---|
| 帧数 / OCR 行数 | 809 / 32,332 |
| 裁图文件 | **32,267 张 / 115.6 MB** |
| 字节唯一的裁图 | 7,554（23.4%）→ 76.6% 是重复内容 |
| 真正送 RapidOCR 的不重复文字 | 2,107 行 |
| 字体校正 | 87 秒；整条后处理 107 秒 |
| 与上一帧完全相同的帧 | 42%（上一场 75.8%） |

结论：空间浪费 3/4，时间花在「同一段文字被反复裁图、反复识别」。

## 16. 改法（A+B+C 全做）

**A. 裁图按内容 hash 命名，同内容只落盘一次**
`Invoke-RegionOcr` 里先编码到内存 → SHA1 前 16 码当文件名 → 见过就复用文件名。
文件数 32k → 7.5k。

**B. 整帧去重**
每帧算整张图的 SHA1；与上一帧相同就直接沿用上一帧的行（含裁图名），
跳过 OCR 与裁图。`structured.jsonl` 照写这一帧，所以「敌名连续 2 帧投票」不受影响。
实测可跳过 42%~76% 的帧。

**C. 边录边认（`ocr-worker.mjs`）**
记录器启动时拉一个后台 node 进程，它每 400ms 扫一次 `linecrops/`：

- 队列静置 1.5 秒或满 200 张 → 调一次 rapid-ocr（批量，避开它 1~3 秒的启动开销）
- 识别完把结果 append 到 `rapid.jsonl`，**并删掉裁图** → 录制期间磁盘几乎不增长
- 收工写 `ocr-stop.flag`，worker 清空队列后写 `ocr-done.ack`，记录器最多等 90 秒

`font-correct.mjs` 改成优先套 `rapid.jsonl`，通常 1~2 秒结束；
worker 没跑或挂掉时，退回原本的批次路径（裁图还在就照旧识别）。

## 17. 顺带修的一个真 bug：PS1 的 BOM 被吃掉

改 `backroom-logger.ps1` 时发现文件头变成 `23 20 ...`（无 BOM）。
PS 5.1 会把无 BOM 的中文当 ANSI 读 —— 整份记录器的中文会变乱码，而**语法检查看不出来**。
已补回 BOM，并在 `verify-final` 加了 `ps1_utf8_bom` 检查（只查真的有中文的 .ps1）。
顺手发现 `player-logger/build.ps1` 也没有 BOM，一并补上。
